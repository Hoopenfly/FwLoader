# FwLoader 产线串口烧录工具 — 说明

> 面向**维护者**的说明。操作员请看同目录的 `使用说明.md`。
>
> 代码里必要的行注释直接写在 `fw_download.ps1` 源码中，本文档只讲设计与协议。

---

## 一、这个工具做什么

把编译好的 `app.bin` 通过串口发给板子，设备端由 FwLoader 库接收并写入升级槽。

全程不需要仿真器，产线只需一根 USB 转串口线。


**完整流程**：

```
① 找固件(app.bin)  →  ② 算整包 CRC16  →  ③ 选串口
④ 依次试 9600/115200/57600/38400：
     拿第一帧当握手帧 → 有应答说明波特率对了(之后就锁定这个波特率)
     然后逐帧发(每帧300字节，失败重传3次、单帧超时3秒)
⑤ 看最后一帧有没有应答 → 判 成功/待确认/失败
⑥ 成功后提示操作员断电重上电(或按复位键)，设备才真正完成升级并启动App
```

---

## 二、协议帧格式

帧头**固定 24 字节**，后面紧跟本帧的数据（最多 300 字节）：

```
$UP OOOOOO TTTTTT CCCCC <DATA>
 ^  ^      ^      ^     ^
 |  |      |      |     +-- 本帧固件数据，最多 300 字节
 |  |      |      +-------- 整包 CRC16，5 位十进制（补零）
 |  |      +--------------- 固件总大小，6 位十进制（补零）
 |  +---------------------- 本帧数据在固件中的偏移，6 位十进制（补零）
 +------------------------- 固定 3 字节
```

以 `app.bin` 41264 字节为例：

```
偏移 0     → 帧长 24+300 = 324 字节
偏移 300   → 帧长 324
...
偏移 41100 → 帧长 24+164 = 188 字节（最后一帧，不足 300）
共 138 帧
```

设备每收一帧回 `$UP <已收字节数>`；出错回 `$` + 英文提示（如 `$CRC ERROR`）。

## 三、几个关键设计（都是踩过坑之后定下来的）

### 1. 串口读取一律用 `BytesToRead` 轮询，绝不用 `ReadLine`

`SerialPort.ReadLine()` 一旦超时会**抛异常**，而 .NET 的 `SerialPort` 在这个异常之后**内部状态就坏了**——端口对象看着还开着，但之后**所有读取都返回空**，只能关掉重建。

这个坑在调试阶段浪费了很多时间：现象是"前几帧正常、某一帧之后再也收不到任何应答"。所以现在 `Read-OneLine` 自己用 `BytesToRead` 轮询 + 累积缓冲拼行，不用任何会抛异常的读取 API。

### 2. `$RxBuf` 必须用 `$script:` 前缀

PowerShell 的函数里直接给外层变量赋值，**只会创建一个同名局部变量**，外面的值不变。半行数据一旦丢在局部变量里，下一行就永远拼不出来。所以读写都显式走 `$script:RxBuf`。

### 3. `'$UP*'` 必须用单引号

PowerShell 双引号会**展开变量**：`"$UP*"` 会把 `$UP` 替换成空字符串，变成 `"*"`，匹配条件永远成立但语义全错。单引号才是字面量。

### 4. 拿第一帧当握手帧

设备的波特率存在 EEPROM 里，现场不一定知道。与其专门发一条探测命令，不如**直接拿要发的第一帧去试**——能收到应答就说明波特率对了，省一次往返。握手只用 2 次重试 × 3 秒，错了就快速换下一个波特率。

### 5. 最后一帧的应答 = 提交确认

设备收完整包固件、整包 CRC16 校验通过后，才会写 `FW_BOOT_FLAG_VALID` 表示"待升级"，而**最后一帧的应答正是在这一步之后发出的**。所以它天然就是"整包已收完并已提交"的确认，工具不需要再发命令去问。

早期版本这里要额外等一轮（30 秒），现在省掉了。

### 6. 最后一帧收不到完整应答，不判失败

设备提交那一刻串口行为特殊，收不到应答属正常现象。此时工具报"**已发送，待人工确认**"而不是"失败"——**误报失败的代价比漏报大得多**：产线操作员看到一个失败提示，可能会把一块已经烧好的板子丢掉重烧。

### 7. 设备不会自行复位

设备复位后，上位机手里那个串口句柄就再也读不到数据了——后续的覆写进度、App 启动信息全部丢失，工具只能靠"猜"判成败。所以设备收完固件只打印提示，**复位交给操作员断电重上电或按复位键**，工具发完就退出。

（这也是为什么设备侧不接受任何"重启"指令。）

---

### 8. 握手成功后不再切换波特率

握手成功就说明**波特率是对的**。后面再丢帧是线路/干扰问题，换波特率解决不了，
只会把已经发出去的进度作废、从头再试一遍。所以一旦握上手，失败就直接判失败。

### 9. 单帧超时 3 秒

正常一帧的往返只要 150ms 左右（324 字节 @115200 传输 28ms + 设备写一页 Flash 110ms + 回包）。
最坏情况（9600 波特率 + 整页擦写）也就 500ms。取 3 秒是留了 6 倍余量。

正常帧**收到应答就立即返回**，所以这个超时只影响真正丢帧时的恢复速度——
单次等待 3 秒。

### 10. 不打印设备的非协议输出

设备在升级过程中会打印 `[BL] BootLoader ...`、`Update(overwrite) 20%` 这类调试信息。
它们不是协议应答，工具只判断"以 `$` 开头"和"不以 `$` 开头"，后者**静默忽略**，
不往屏幕和日志里写——否则会污染协议日志、干扰操作员看进度。

（代价：设备中途意外复位时，那些启动横幅也看不到了。排查这类问题要临时把
`Send-Frame` 里的 `Write-Log ("设备: " + $line)` 加回来。）

## 四、常见问题

| 现象 | 原因 / 处理 |
|---|---|
| `未检测到串口，请检查串口线插入状态(按 Q 退出)` | 把线插上即可，**工具会自动继续**（按 `Q` 放弃退出） |
| `无法打开串口` / 串口被占用 | 关掉串口助手、Keil 的串口窗口等占用该串口的程序 |
| 4 个波特率全部`无应答` | 板子没上电、串口线接错（TX/RX 反了）、或板子不在升级模式 |
| 某一帧`发送失败` | 线路干扰。工具已自动重传 3 次、单帧超时 3 秒；反复失败检查线材和接地 |
| 烧到一半突然 TIMEOUT | 设备中途被复位了（DTR/RTS 抖动，或有人按了复位键）。IAP 会话状态已清零，**必须从头重烧** |
| `已发送，待人工确认` | 设备大概率已经收好了，手动复位并观察 App 是否启动 |
| 提示`固件已提交，请手动复位` | **正常成功**。断电重上电或按复位键，BootLoader 会自动完成升级 |
| **双击 bat 报一堆 `Unexpected token`** | `fw_download.ps1` 丢了 UTF-8 BOM。PowerShell 5.1 会把无 BOM 的 UTF-8 当 GBK 读，中文注释一乱就破坏语法。用记事本"另存为"选 UTF-8 即可 |

日志文件在 `log\flash_<时间戳>.txt`，出问题时可回溯每一帧的收发记录。

## 五、与设备端的对应关系

| 工具侧 | 设备侧 |
|---|---|
| `Get-Crc16`（初值 0xFFFF，多项式 0xA001） | `fw_iap.c` 里的 CRC16-Modbus |
| 帧头 `$UP OOOOOO TTTTTT CCCCC ` | `fw_iap_parse_text_frame()` |
| 每帧 300 字节 | `FW_IAP_TEXT_DATA_MAX = 300` |
| 帧总长 324 字节 | 设备接收缓冲 `COM1_RX_BUF_SIZE = 340` |
| 应答 `$UP <已收>` | 文本协议正常应答 |
| 错误 `$...` | 文本协议错误应答 |
